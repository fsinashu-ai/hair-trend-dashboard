【追加の実装依頼・返答は日本語で】

1. 目的
`tools/search-console/inspect-urls.mjs`（URL 検査の道具）を直し、日本語スラッグの記事を正しく調べられるようにする。
2026-11-27 の調査で、サイトマップにある小文字の `%e9%ab%aa…` 形式の URL を渡すと、Google の答えが「URL が Google に認識されていません」になった。同じ URL を大文字の `%E9%AB%AA…` 形式で渡し直すと、5件中4件は登録済みだった。
あわせて、同じ日に何回か実行すると結果のファイルが上書きされて、前の結果が消える問題も直す。

2. 対象
- 変更: `tools/search-console/inspect-urls.mjs`
- 変更: `tests/search-console-inspect.test.mjs`
- 変更: `docs/blog-workflow.md`（「8. 数日後の確認」の使い方に、日本語の URL もそのまま渡せることと、同じ日の結果は追記されることを1〜2行足す）

3. 変更してよい範囲
上の3ファイルだけ。

やること
- 検査に送る前に URL をそろえる関数（例: `normalizeInspectionUrl`）を作り、`main` で使う。
  - パスとクエリの `%xx` を大文字にする（例: `%e9` → `%E9`）。`%` に続く2文字が16進数のときだけ変える。
  - 日本語のまま渡された URL（例: `https://ef-mayke-s.com/single-post/髪質改善と縮毛矯正は何が違う？/`）も、大文字の `%XX` 形式になるようにする（`new URL()` の `href` を使えばよい）。
  - ホスト名、ほかの文字、末尾の `/` は変えない。
- 結果のファイル（`runtime-data/search-console/inspect-YYYYMMDD.md`）は、同じ日のファイルがすでにあるときは上書きしないで、末尾に追記する。追記するときは、区切りの行と実行した時刻（日本時間）を入れる。
- 結果の見出しの URL は、実際に Google へ送った形（そろえた後の URL）にする。そろえる前と違うときは、見出しの下に1行「入力: <元の URL>」と書く。
- 1回に渡せる件数（20件まで）は変えない。

4. やってはいけないこと
- 秘密鍵・アクセストークン・`.env.local` の値・鍵ファイルの場所や中身を、画面・ファイル・ログ・テストに出すこと。
- `.env.local` や鍵ファイルを読む・開く・作る・変えること（テストも含む）。本物の Google にアクセスすること。
- `webmasters.readonly` 以外のスコープを使うこと。書き込みの操作（登録リクエスト、サイトマップ送信など）をすること。
- 指定した3ファイル以外を変えること。依存関係の追加、`git commit`、`git push`。
- 作業の前に `git status` を確かめ、ほかの人のまだコミットしていない変更を戻したり上書きしたりしないこと。

5. 完了条件
テストで次のことを確かめている。
- 小文字の `%e9%ab%aa` が `%E9%AB%AA` になる。
- 日本語のままの URL が、大文字の `%XX` 形式になる。
- 英数字だけの URL は変わらない。
- `%` の後ろが16進数でないところは変わらない。
- Google に送る `inspectionUrl` が、そろえた後の URL になっている。
- 同じ日に2回保存すると、1回目の結果が残り、2回目が追記される。ファイルへの書き込みはテストで差し替え、本物のファイルは使わない。

これまでのテストもすべて通る。`npm.cmd test` と `npm.cmd run lint` が通る。

6. 確認方法
`npm.cmd test`、`npm.cmd run lint`。本物の API での確認は、トレンド・SEO部署が行う。

7. 報告の形
